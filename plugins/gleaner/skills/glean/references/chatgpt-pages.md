# ChatGPT editable Page clips

## Host boundary and routing

Use this reference only when the active assistant host is ChatGPT and an explicit destination request selects an editable Page, the built-in Page default applies to a new save or find, an update targets a retained Page, a read-only presentation or export request names one, a follow-up explicitly identifies a Page clip (including one from an earlier session), or a find is explicitly scoped to Pages. An article called a page, a selected Page, or visible Page tools alone do not select this destination. Never use this route in Claude Code, Claude web, Cowork, or the Chrome side panel hosted by Claude, even when Page tools are visible. Those hosts keep their existing defaults, formats, and behavior.

This reference takes precedence over glean's generic save, update-failure, and full-preview instructions only for the selected ChatGPT Page route. It changes storage and presentation, never source extraction or the evidence needed for a video summary. Continue glean steps 1–5 and the YouTube blocked-content rules. Never create a Page for blocked content until those rules authorize a clip.

Honor existing explicit-request precedence: a destination flag beats destination wording. Thus `--to chat` with “as a Page” still selects chat. `--to page` is ChatGPT-only and per-save, not a schema-1 preference provider. A retained Page is a session override for that clip only, not the next unrelated save. Keep `--to chat`, `--to drive`, `--to notion`, `--to artifact`, local paths, saved defaults, and the shared preference contract unchanged. A different explicit destination creates a separate clip through its existing route; Markdown export alone is not a destination change.

Call the destination a Page, not Canvas. For a request for Canvas alone, explain that editable Pages are supported when tools are available and ask whether a Page meets the request; do not silently substitute it or claim traditional chat Canvas support. Pages are the ChatGPT built-in default, not a storable provider. On “always save as a Page,” explain this behavior without writing preferences. If a saved destination wins, explain the conflict; remove it only on an explicit request through normal preference operations. Page clip-list destinations remain unsupported.

## Destination resolution

Load and validate preferences and resolve enabled sync before choosing a destination. Resolve in order: explicit destination flag, explicit destination wording, identified retained clip destination and format, session destination, project destination, user destination, then built-in host default. Collected-part flags retain their existing precedence. Track per-save provenance as explicit, retained clip, session, project, user, or built-in default in session memory only, never shared preferences. Invalid stores, unresolved sync conflicts, and unreachable configured destinations retain existing recovery; never treat them as absent configuration.

Only a new unconfigured ChatGPT save uses the built-in Page default. When only that default would apply, a winning explicit or saved raw Markdown format uses existing Markdown chat/file delivery; an explicit HTML chat-file request likewise uses its existing route. Do not ask about an incompatibility created solely by the built-in default. Explicit Page plus raw-file-only delivery still requires a choice. A retained destination applies only to its identified clip, never the next unrelated save.

## Capabilities and format

Discover tools actually exposed in this session, then follow their current schemas and the host's Page creation/editing instructions. Do not assume tool names or APIs from an earlier session. A new editable clip requires create, read, and edit capabilities; an existing clip requires read and edit. Discovery is not proof of permission. Never grant access, connect an account, sign in, share, or enable automations to make the destination work.

Run glean's shared preference resolution, including enabled sync, before duplicate checks. Keep invalid-store and unresolved-conflict handling. Page content is native editable Markdown blocks, not a raw `.md` file. An explicit Page destination with no explicit format requests native delivery for this save, without changing a saved format setting. An explicitly combined Page and raw-Markdown/HTML-only request needs a choice between native Page delivery, a file, or Page plus an export. Do not silently discard an explicit format request. No preference schema or stored values change.

Before any write is attempted, missing required tools permit automatic Markdown chat/file fallback only for the built-in default; explain once that Pages are unavailable here and identify what was actually delivered. For explicit or retained Pages, missing tools require an alternative choice. Access denial or confirmed write rejection on any Page route requires reporting the failure and offering a choice, never silent fallback. Wait for that choice rather than silently changing destination. After an attempted creation or update, report a confirmed rejection as not committed only when the tool establishes that outcome. If a write may have committed or readback fails, report the outcome as uncertain or verification pending, retain any returned Page ID, canonical URL, creation key, and original arguments, and reconcile the same operation before offering another save. Do not claim no Page was saved merely because readback lost access, and do not prompt for a duplicate creation. Do not probe other accounts or destinations after a refusal.

## Identity and duplicate handling

Retain a separate session delivery record beside the unchanged bookmark model: bookmark ID, canonical Source URLs, Page ID, returned canonical URL, creation key and original creation arguments, and confirmed save/update state. Keep this out of preferences and the full clip. The Page ID is not a file path, an artifact ID, or a browser tab ID. Use returned IDs and URLs only.

For the same source saved to a Page in this conversation, reuse that retained Page ID unless the request explicitly asks for a new clip. For answers without a Source, use retained clip identity; never collapse unrelated answers by their missing URL. A move from chat/file to a Page creates one new stored clip from the existing content without another extraction. Keep the earlier file unchanged and describe the copies accurately.

When locating an older Page clip, use an available Page search tool and read candidates to verify Saved, Category, and canonical Source (or answer identity). A search hit by title alone is insufficient. Search within the named destination when one was specified; follow returned pagination. Exclude indexes and non-clip Pages. Ask which one when matches are ambiguous. An empty bounded search is not proof that no duplicate exists; disclose unavailable or incomplete duplicate checks. Do not run an unscoped Page search on ordinary non-Page saves or finds.

Keep glean's earlier-session updated-copy policy: show a verified duplicate and offer updated copy or skip; do not overwrite or delete the older Page. A follow-up to an earlier-session clip follows follow-up's updated-copy rule, using a new Page and a Supersedes link. Later edits in this conversation update that new copy. A title/source match does not convert an earlier-session clip into a same-session clip.

## Create and verify

1. Build the full clip and bookmark once from the existing summary workflow. Preserve Source, Channel, Saved, Category, Type, Tags, notes, parts, code, timestamps, Supersedes, Follow-ups, and source limitations. Do not fetch again merely to create a Page.
2. Create a private Page with no parent or Space unless the request names a verified destination. Do not change sharing, ownership, collaborators, or automations. Use the native title; remove only its duplicate opening title from the body and adapt heading levels to host guidance. Keep ordinary text editable; do not substitute HTML, images, or an interactive viewer for the clip.
3. Generate and retain one idempotency key and the exact creation arguments before creation. If the outcome is uncertain, reconcile using the host's supported lookup/read or retry the same key and arguments as instructed. Never retry with a new key or generate a replacement Page merely because creation timed out.
4. Read back the returned Page and its guidance. Verify title, metadata, complete content, Source, timestamps, notes, and limitations. Retain the actual canonical URL. A returned ID or successful tool invocation alone is not complete verification. If readback fails, record verification pending; reconcile the same Page, not a new save.
5. Record a successful receipt only after verification. In the existing bookmark, use a session-only destination record for the Page and its returned ID, and put only the verified canonical URL in saved locators. Do not add Page fields to the shared model or preference schema.

Keep the full clip's final copyable follow-up prompt. After creation returns a URL, make its search location the verified Page link, using host-guarded edits if needed, rather than claiming the Page is merely a chat attachment. Verify that change without creating another copy.

## Edit and reconcile

Read current Page content and Page guidance before each edit; this is the authoritative clip, including manual changes. Use the same Page ID and stream from the read. An unqualified “add the tools” may use the clearly identified retained clip; ask when several clips are plausible. Never choose an unrelated selected Page or reconstruct missing content from memory.

Find the target section in the current blocks. Use guarded literal patches for text within one existing block and structural operations for new headings, sections, or list items. Copy block IDs and hashes from the read and sequence guards when provided. Use supported atomic batches when one requested change must apply together. Do not replace the whole Page from a stale attachment or cached bookmark. Preserve unrelated text, manual notes, links, metadata, and earlier Follow-ups.

Inspect commit status and every operation result, including ignored/deleted-target results. On stale guards, reread and rebuild only unapplied changes. On an unknown outcome, read and reconcile before another write. Never replay an applied insertion. A repeated request should update or retain the existing section, not duplicate it; if the requested content is already present, skip the write and report it unchanged. Follow the host's recovery guidance and stop if it does not permit a safe retry.

Read back new sections and preservation-sensitive edits to verify their final content. Only then refresh retained bookmark content from the current Page. A failed, read-only, deleted, or inaccessible Page is not permission to create another Page or publish an updated copy. Leave the original intact and offer an explicit recovery choice. Do not use glean's generic automatic update-failure copy or fallback for this route.

Follow-up suggestions use the same Page adapter: verify the clip headers, review the current content, and add the dated suggestions just above the final follow-up prompt's divider. Keep exactly three suggestions or follow-up's ask-instead behavior. Preserve earlier dated suggestions. The retained Page, not a stale file or chat rendering, supplies current content.

## Confirm, export, and find

After verified Page creation or an update, preserve the existing full in-chat clip output: summary, details, metadata, source links, tags, limitations, timestamps, and preview behavior as applicable. Add a short save/update confirmation and verified canonical Page link alongside it. Save the complete clip from the same source-grounded content; do not replace chat output with a link-only receipt or require another request to see it. Honor an explicit short response, Page-only delivery, or current-request preview control. Follow-up additions preserve current in-chat response behavior while updating the same Page. Report persistence failures separately without suppressing available in-chat content or claiming a successful save. Keep the normal chat tag and requested clip-list/index maintenance with verified Page links; an index failure never repeats the clip save or creates a collection.

If the request says “show the full clip here,” or complains that the Page cannot be read in chat, read the current Page and render the full clip inline as presentation recovery, without another save. If read access is lost, say so; do not present stale content as current. Do not claim the Page opens a particular mobile pane or changes Android attachment behavior. Inspect a rendered preview when available; saved Markdown alone does not establish visual or device compatibility.

Export Markdown only when requested. Read the current Page, including manual edits, and generate the file through the host's supported file-delivery mechanism, using the native Page title as the export title. Keep export and Page receipts separate. A failed export does not invalidate a successful Page edit; an older export is not automatically synchronized. Do not automatically generate HTML companions. Ordinary non-Page saves and all Claude HTML/Markdown behavior remain unchanged.

For a find explicitly scoped to Pages or using the resolved built-in Page default, use Page search and read verified clip metadata, return glean's existing result table, and disclose bounded or incomplete results. Include retained Page clips in this conversation's results without a search when sufficient. Never make Page search a new default across Claude or unrelated destinations.
